a machine's public door; someone on the LAN or the tailnet at the control port; the holder of a

### SM-133 A websocket through a machine's door reaches every service past the door's rules and the wall (high)

Area: the proxy, the doors. How many: one path, the `upgrade` handler of the service port;
every service on the host.

`src/main/src/helpers/tunnel_inbound.js:44`

```
    stream.tunnel_from = remote.name;
    app.servers.server.emit('connection', stream);
```

`src/main/src/helpers/server_start.js:50`

```
    out.on('upgrade', function (req, socket, head) {
        ...
        const host = String(req.headers.host || '').toLowerCase().split(':')[0];
        if ((app.config.control.host !== null) && (host === app.config.control.host)) {
            handle_control_upgrade(app, req, socket, head);
            return;
        }
        const promise = handle_upgrade(app, req, socket, head);
```

`src/main/src/routes/handle_upgrade.js:26` then routes by the hostname alone:
`const route = route_from_request(app, host, pathname);`.

What an attacker does: a machine's agent relays what its door table cannot route, upgrades
included (`src/agent/src/agent_door_answer.js:65-72`, `docs/remotes.md:537-539`), before it
strips `X-Auth-User` (`:82-90`). A plain request on such a stream is held to the door's rules,
the wall and the `off` switch (`handle_request.js:56-80`); an Upgrade request is not: the
handler above hands it to `handle_upgrade`, which picks the service by its published hostname
and forwards every header as sent (`proxy_upgrade.js:19`, `headers_forwarded.js:7-12`). Anyone
at a machine's public front sends a websocket handshake with `Host: <any published name>` and
`X-Auth-User: victim@example.com` and reaches that service as that user, though the door never
named it, it is switched off, or a wall stands in front of it. With `exposed` on, the image's
default (`config/serviceman.json:3`), the same stream reaches `/api/v1/shell` through
`handle_control_upgrade.js:45`, which asks `control_allowed` only, against `docs/deploy.md:156`
and the comment at `handle_request.js:53` ("the control page never among it").

What it would take: in the `upgrade` handler of `server_start.js`, or at the top of
`handle_upgrade`, the same door reading as `handle_request.js:56-80`: a `tunnel_from` stream is
answered only by the service its door rule names, after the wall, never by the control host,
and `x-auth-user` is stripped there. One shared helper for both paths.

Prior: new. Confirmed by: `probe_tunnel_upgrade.js` on an in-process serviceman with `echo` at
`echo.localhost` and a door rule for `walled.example.com` only. Through a stream marked
`tunnel_from='vps1'`: a plain GET with `Host: echo.localhost` answered 404; a websocket GET
with the same Host and `x-auth-user: forged@example.com` answered 101, and the echo server saw
`X-Echo-Host: echo.localhost | X-Echo-User: forged@example.com`. With `exposed: true` a websocket
to `/api/v1/shell?service=echo` with the owner's token and the control Host answered 101
through the same stream; with `exposed: false` it was closed.

### SM-134 One shell websocket frame, or a docker resize with bad numbers, kills serviceman (high)

Area: the shell and terminal websockets. How many: three join handlers (a container shell, a
service shell, a machine terminal) through one `terminal_attach`; two docker resize callbacks.

`modules/terminal/server/terminal_attach.js:25`

```
        if (message.type === 'input') {
            stream.write(message.data);
            return;
        }
```

`src/main/src/routes/handle_control_upgrade.js:161` (and `:190`)

```
        resize: function (size) {
            docker_exec_resize(connect, exec.id, size);
        },
```

`src/main/src/helpers/docker_exec_resize.js:10`

```

```

What an attacker does: whoever may open a shell (the owner; a token with `terminals` on its
machine through a kept terminal's stream, `handle_control_upgrade.js:62,123-138`; through
SM-133 with `exposed` on, anyone at a machine's door holding a token) sends
`{"type":"input","data":123}` or `{"type":"input","data":null}`. `stream.write` throws
`ERR_INVALID_ARG_TYPE` or `ERR_STREAM_NULL_VALUES` inside the websocket's message handler,
nothing catches it, `src/main/index.js` sets no `uncaughtException` handler, and the process
exits: every container, program, forward and visitor on the host goes with it. A resize frame
is the same class: `cols` and `rows` reach `docker_exec_resize` unchecked and `http.request`
throws `ERR_UNESCAPED_CHARACTERS` inside the promise's executor, an unhandled rejection, fatal
on Node 24. The machine terminal's resize is guarded (`:234-237`); the two docker ones are not.

What it would take: in `terminal_attach.js`, `String(message.data)`, `cols` and `rows` checked
as small integers, each handler in a try/catch that closes only that socket; a `.catch` on the
two `docker_exec_resize` calls.

Prior: SM-07 (high), open; the fix the 2026-09-24 note asked for was not applied. Confirmed by:
`probe_terminal_attach.js` against the scratch copy's `terminal_attach` with a PassThrough as
the far end: `data: 123` gave an uncaught `ERR_INVALID_ARG_TYPE … Received type number (123)`,
`data: null` an uncaught `ERR_STREAM_NULL_VALUES`; `docker_exec_resize(connect, 'abc',
{cols: 'x&y=1', rows: {}})` ended the process with `ERR_UNESCAPED_CHARACTERS`.

### SM-135 A secret under the service name `constructor` kills the host (high)

Area: the secrets API. How many: one route, `POST /api/v1/secrets`.

`src/main/src/routes/handle_control_request.js:135`

```
const RE_SECRET = /^[a-zA-Z0-9][a-zA-Z0-9_.-]*$/;
```

`src/main/src/routes/handle_control_request.js:1471`

```
    const bag = (service === '') ? kept.global : ((kept.services[service] === undefined) ? {} : kept.services[service]);
```

`src/main/src/helpers/secrets_read.js:46` builds the map of services as `const out = {};`.

What an attacker does: with the owner's token, or a signed-in page reached through SM-133,
`POST /api/v1/secrets {"service":"constructor","name":"keys","value":"x"}`. `RE_SECRET` accepts
`constructor` (it begins with a letter; `__proto__` is refused for its underscore);
`kept.services.constructor` is the inherited `Object` function, not `undefined`, so the bag is
`Object` and `bag.keys = 'x'` overwrites `Object.keys` for the whole process. The next log
line, `log_words` calling `Object.keys`, throws inside the shared `answer()` catch itself
(`server_start.js:151`), and the process is gone. Nothing is persisted, so a restart recovers;
one request repeats it.

What it would take: the bags and the maps built with `Object.create(null)` and read with
`Object.hasOwn`, in `secrets_read.js:32,46`; `constructor` and `prototype` refused by
`RE_SECRET`; the same wherever a request's key indexes a plain object: `app.remote_by_name` and
`app.service_by_name` are `{}` too (`app_from_config.js:15,17`), which is why
`/api/v1/remotes/constructor/ports` answers 500 and not 404 (SM-151).

Prior: SM-08 (high), open. Confirmed by: the scratch instance; `{"service":"__proto__",…}`
answered 400, `{"service":"constructor","name":"keys","value":"x"}` reset the connection and
`pgrep` showed the process gone; its stdout ended `TypeError: Object.keys is not a function or
its return value is not iterable at log_words (src/helpers/log_words.js:17:31) … at
server_start.js:151:9`.

`serviceman.js`).

Prior: SM-09 (high), partly fixed. Confirmed by: read; not driven (no docker engine in the

### SM-140 Self-update replaces the running agent with no integrity check, over a plain link (medium)

## What held, by area

- **Control API and proxy:** no token or a wrong one answers 401 and a browser the sign-in
  page; only the owner's token opens a session; every write and every websocket wants the same
  origin; a foreign Host is a 404; scoped tokens stop at their rights and machines on every
  route probed; a `files` token without folders is refused; one agent per remote token; secrets
  listed by length only; config writes serialised, validated and renamed in; JSON bodies capped
  at 1 MiB; static files confined; the waiting and error pages escape their text; the proxy
  drops hop-by-hop headers and trusts `x-forwarded-proto` only through a tunnel; `/redir` uses
  a host from the config; two replaces at once answer 409.
- **Agent and modules:** a scoped token's root is enforced for every path, links resolved
  before the compare (probed); tar names go as `./<name>` (probed with
  `--checkpoint-action`); apt takes no names from the link; ufw is argv behind an allowlist,
  newlines refused; the volume key goes by stdin only and never over plain http; `du` is
  bounded; programs are re-adopted across a reconnect; the peer port is token-gated and
  tailnet-only; state files 0600; the root half runs fixed argv; terminal names and signals
  checked; no shell strings from link parameters; no tar traversal; reads bounded.
- **Pages:** every `v-html` draws an icon from a constant table; no `innerHTML`, `eval`,
  `srcdoc` or `postMessage`; hrefs carry fixed schemes; names and lines render through `{{ }}`;
  xterm gets bytes only; no token in storage or the URL; the cookie is HttpOnly and Strict.
- **Logline and web-terminal:** Logline's token compared whole in constant time and bound to
  an address; bodies capped; every query parameterised, read-only user, private nets only;
  tokens issued to admin addresses only. web-terminal's `/_/` names have no slash.
- **Build and repository:** the installer writes its env with umask 077; the served agent is
  built from source; tracked files hold no secret and no real machine name; `.gitignore` keeps
  `.env`, `data/`, sockets and the local config out; the vendor versions equal `package.json`.
- **Logs:** query values masked; `term_create` logs env names only; the volume key never;
  `log_words` quotes what is not a bare word.
