# Project audit — 2026-09-24

Repository: `/app` (serviceman), not a git checkout: there is no `.git`, so there is no
branch, HEAD or history to cite. 288 JavaScript and CSS files were linted. Source is about
22,000 lines and tests about 6,300 (inventory in the appendix). Times in this note are
Europe/Chisinau (UTC+3).

## Scope

This is the first audit of this project. `notes/` held no earlier `audit-*.md`, so section 8
lists only what was found and fixed earlier today.

Checks run:

- **Read in full**, by six parallel readers plus this note's author: every file under `src/`
  (host routes, host helpers, control page, skins, agent, shared helpers), every test,
  fixture and fake under `tests/`, `bin/*`, both Dockerfiles, the entrypoint, `README.md`,
  `docs/*.md`, `notes/*.md`, `examples/*`, `.env.example`, `config/index.js` and the stray
  root files. Minified files under `src/main/public/vendor/` were checked for version only.
  The built `serviceman-agent.js` was rebuilt from source and diffed rather than read.
- **Tests**: `npm test`, 165 of 165 pass in 83 s.
- **Rulebook lint**: vbarbarosh/rules at `6521671` cloned into the scratchpad, then
  `eslint --config eslint.projects.config.js "src/**/*.{js,css}" "tests/**/*.js" "config/**/*.js"`.
- **Driven, not only read.** Each reader started its own serviceman on free ports, with
  `SERVICEMAN_STATE_DIR` in the scratchpad and the fake docker from `tests/bin` on `PATH`, and
  a real agent from `src/agent` dialled in. Probes: cross-origin writes, malformed and
  oversize bodies, wrong Host headers, traversal, 20 concurrent config writes, a read-only
  state dir, hostile strings in names and titles, shell websocket frames, prototype keys.
  Lifecycle races were driven with small scripts on the test fixtures: stop during start,
  a link drop mid-request, abandoned queue waiters, multi-machine wake, crash loops, config
  edits with a restart pending. The agent was driven for apt, tar, file put, program install,
  a hung docker, and a silent server.
- **Control page in Chromium** through Playwright: light and dark OS schemes, the theme
  switch clicked and reloaded, blocked `localStorage`, 1280 px and 375 px, every pane and
  form, an invalid form, and 2.5 minutes open while counting requests and heap.
- **Live evidence, read only.** The host logs in `data/logs/` (26 files, 352,714 lines,
  2026-08-22 to today) and the server agent logs from `server-logs.zip` (32 files,
  191,973 lines) were grepped for failures, secrets, unmatched begin lines and shape breaks.
- **Doc checks.** Every JSON config example in `docs/` was run through `config_from_json`.
  Every internal markdown link was resolved. Every named field, default, route, env
  variable and log sender was grepped for in the source.
- `npm audit`, `npm outdated`, a secret-pattern scan outside `node_modules/` and `data/`,
  file modes of `data/`, and a vendored-library comparison with `package-lock.json`.

Not exercised:

- The live instance, its sockets and the real remotes. The live config was read only for
  shape, key names and file modes.
- Real docker, apt, dconf and screenshots. Only the fakes in `tests/bin` were used.
- Docker images were not built. `Dockerfile.agent`'s build step was replayed in a scratch
  copy. `bin/build`, `bin/configure`, `bin/release`, `bin/run`, `bin/vendor`, `bin/watch` and
  the entrypoint were read, not run, because they write into the tree or start containers.
- Interactive terminal typing, file-manager uploads and downloads in the browser, the
  non-ledger skins (they do not exist), keyboard-only navigation and screen readers.
- TLS branches, autoscale under real load, and races between image pulls and requests.

## Verdict

Serviceman does its main job well. The link protocol, flow control, log shape and config
validator are careful, and 165 tests exercise them end to end over a real link. The risk sits
at the trust boundaries, and it is severe:

- The control API has no password and no cross-origin check. Any web page open on the host
  machine can create a service that runs a command on every remote. The live config also
  exposes that API on all interfaces.
- On a machine, the agent reaches the whole filesystem. Its root half runs package names
  through a root shell and executes a file the unprivileged user owns. Its tar download
  treats file names as tar options.
- A Google OAuth client secret sits in world-readable host and agent logs.
- Three single requests kill the host process.
- Several lifecycle races leave containers running untracked or requests failing for good.
  Each was reproduced.
- Two build and deploy paths are broken, and the docs describe an older system in places.

| Area | Health | In one line |
|---|---|---|
| Control API and proxy | poor | CSRF to command execution; two one-request crashes; files served on the control origin |
| Agent and root half | poor | whole-filesystem reach, root shell injection, root runs a user-owned file |
| Secrets | poor | client secret in world-readable logs; tokens in a 0644 config |
| Service lifecycle | fair | common path correct; stop/start, queue and reconnect races proven |
| Remote link | good | careful framing and flow control; the watchdog flapping was fixed today |
| Logs | fair | shape holds on 352,714 lines; free text and relayed output are not encoded |
| Config validation | fair | refuses the important collisions; accepts many bad values silently |
| Control page | good | escaping, theme switch and phone layout work; dies when storage is blocked |
| Docs | drifted | security scope understated; defaults, launcher and ping model stale |
| Tests | good | 165/165; secrets, boot and shutdown untested; a few timing-sensitive tests |
| Build and deploy | poor | agent image cannot build; compose loses state; bundle a month stale |
| Dependencies | good | `npm audit` clean; Vue one patch behind |
| Rulebook conformance | fair | 284 lint errors, mostly operator spacing; sender and `out` rules broken in places |

## 1. Control API and proxy

### SM-01 Any web page can write to the control API and run commands on every remote (critical)

The only gate before a write is `control_allowed` and `control_host_allowed`
(`src/main/src/routes/handle_control_request.js:146`). Neither looks at `Origin` or
`Sec-Fetch-Site`, and bodies are parsed whatever their type:
`service_from_body(JSON.parse(await body_read(req, BODY_LIMIT_BYTES)))` at `:1379`. A
`text/plain` POST is a CORS simple request. A browser on the host sends it from 127.0.0.1 with
`Host: localhost:<port>`, so both checks pass.

Reproduced against a scratch instance:

```
curl -X POST http://127.0.0.1:47081/api/v1/services -H 'Host: localhost:47081' \
  -H 'Origin: https://evil.example' -H 'Content-Type: text/plain;charset=UTF-8' \
  --data '{"service":{"name":"pwn","type":"shell","remote":"ui1","command":"id > …/pwned.txt","policy":{"start":"always"}}}'
→ 200 {"ok":true,…,"notes":["pwn: new service"]}
log: program_begin … argv="/bin/sh -c id > …"     pwned.txt: uid=1000(ubuntu) …
```

Any page the operator visits can run commands on every machine, rewrite the config, add a
remote or change the join token. DNS rebinding of the control hostname is correctly refused
(`Host: evil.example` gets 404). This is the plain cross-site case, which that check does not
cover.

Fix: refuse every non-GET, non-HEAD request whose `Origin` or `Sec-Fetch-Site` is not the
control page's own, and require `content-type: application/json`. Apply the same check to
the websocket upgrades in `handle_control_upgrade.js:35`.

### SM-03 The live config opens the passwordless control API to every interface and every local user (high)

`data/serviceman.json:8-12` sets control `bind` 0.0.0.0, port 3001, `exposed: true` and
`socket_mode` "0666". `control_allowed.js:10` then lets every caller in:
`return app.config.control.exposed || from_this_machine(req);`. The Host check is no barrier
to a direct request, because the caller chooses the header. The socket is `srw-rw-rw-`.

So anyone who can reach port 3001, and any local user through the socket, has the whole
API. That means the remote tokens through `GET /api/v1/config`, shells on every machine, and
SM-02's root on every machine that has a root half. The comment at `control_allowed.js:7`
says `exposed` is "for whoever puts their own wall in front". This deployment has no wall in
the repository. The agents dial port 3001 over tailscale (`100.64.0.20:3001` in the agent
log), so the tailnet is the likely perimeter. That was not tested against the live host.

Fix: turn `exposed` off, or put an authenticating proxy in front of 3001. Use socket mode
0660 with a group.

### SM-07 One shell websocket frame with a non-string `data` kills the host (high)

`handle_control_upgrade.js:142` (machine shell) and `:94` (container shell) call
`stream.write(message.data)` on `message = JSON.parse(String(raw))`. A number or an object
makes `write` throw `ERR_INVALID_ARG_TYPE` synchronously inside the `message` handler. Nothing
catches it, so the process exits. `cols` and `rows` of a resize are not checked either.

```
ws://127.0.0.1:47081/api/v1/shell?remote=ui1  ←  {"type":"input","data":123}
serviceman exits: TypeError [ERR_INVALID_ARG_TYPE]: The "chunk" argument must be … Received type number (123)
    at handle_control_upgrade.js:142:20
```

Fix: coerce `data` with `String()`, check `cols` and `rows` as small integers, and wrap each
handler in try/catch that closes only that socket.

### SM-08 A secret stored under service `constructor` replaces `Object.keys` and kills the host (high)

`secrets_read.js:44` builds the per-service bags with `const out = {}`, which inherits
`Object.prototype`. `handle_control_request.js:1175` picks the bag with
`kept.services[service] === undefined ? {} : kept.services[service]`. `RE_SECRET` at `:87`
accepts `constructor`, so the bag becomes the global `Object` function, and `bag[name] = value`
assigns to it.

```
POST /api/v1/secrets {"name":"tok","value":"abc"}                        → 200
POST /api/v1/secrets {"service":"constructor","name":"keys","value":"x"}  → connection reset
serviceman exits: TypeError: Object.keys is not a function  at log_words (src/helpers/log_words.js:14)
```

Fix: build the bags with `Object.create(null)` and test with `Object.hasOwn`. Refuse
`__proto__`, `constructor` and `prototype` in `RE_SECRET`, `RE_TOOL` and machine keys.

### SM-09 Remote files are served inline as HTML on the control origin (high)

`GET /api/v1/remotes/<name>/fs/file/<path>` (`handle_control_request.js:648-683`) streams a
remote file with `content-type` from `mime_type_from_path` (`:673`) and
`content_disposition('inline', …)` (`:675`). That is the same origin as `/api/v1/config`,
which returns the raw config with the remote tokens. The page prefers a separate
`<name>.fs.<control host>` origin (`public/serviceman.js:1268-1278`). It falls back to this
route when the machine name has a dot or there is no control host, and the route answers
anyone either way.

```
curl -si '…/api/v1/remotes/ui1/fs/file/…/evil.html'
→ 200  content-type: text/html; charset=utf-8  content-disposition: inline
   <script>fetch("/api/v1/config")…</script>
```

An HTML file on any machine, opened through this route, runs script with the control page's
authority.

Fix: serve remote files as attachments with a neutral type, or add
`Content-Security-Policy: sandbox` here. Better, answer this route only on the `.fs.` origin.

### SM-24 Bad JSON answers 500 and an oversize body resets the connection (medium)

`JSON.parse(await body_read(…))` throws into the shared `answer()` catch
(`server_start.js:142-149`), which answers 500 with the parser's message. `body_read.js:9-12`
destroys the request when the limit is passed, so the client sees a reset, not 413.

```
POST /api/v1/services --data '{bad'           → 500 "Expected property name or '}' in JSON at position 1"
POST /api/v1/config/check --data-binary @2MB  → Recv failure: Connection reset by peer
```

Fix: catch parse and size errors where the body is read, and answer 400 and 413 as JSON.

### SM-25 Visitors see raw error text: status.json, the 500 page, a corrupt secrets file (medium)

Three paths skip the masking that `error_detail.js:13-19` gives the HTML error pages:

- `handle_request.js:163-173` sends `error: service.state.last_error` and `said:`, the
  program's install and output lines, raw to any visitor under `/__serviceman__/`.
  `docs/deploy.md:214-217` promises "no ports, no container names, no docker output, no remote
  names". Reproduced: with the remote offline, `status.json` answered
  `"error":"app: remote vps1 is offline — no machine to start it on"`. The test meant to guard
  this, `tests/control_access.test.js:85-90`, only checks an all-null body.
- `server_start.js:147` renders `error.message` on the shared 500 page for both doors. A
  read-only state dir showed `EACCES: permission denied, open '…/serviceman.json.serviceman-save'`
  on the control door. The public-door case was read, not forced.
- `secrets_read.js:20` parses `secrets.json` without a catch. Node 24 quotes the source in
  some parse errors (tested: `Unexpected token 'S', "{"a": SECRETVALUE}" is not valid JSON`).
  That message becomes the start error, and `error_detail.js:15` shows real reasons to every
  visitor when `control.exposed` is on, as it is live.

Fix: pass all three through `error_detail`/`said_of`, and throw a fixed message for a corrupt
secrets file.

### SM-53 The error page title and the waiting page's inline JSON are not escaped (low)

`render_page.js:121` writes `<title>${page.title}</title>`, and `render_error_page.js:60`
passes the title raw while escaping the `h1` at `:58`. `handle_request.js:249,261` put
`${service.title} did not start` there. A title of
`</title><script>alert(document.domain)</script>` rendered as live script. The page is served
on the service's hostname to visitors. `render_waiting_page.js:81` puts `JSON.stringify(prefix)`
inside a `<script>`, and `assert_service_valid.js:132` accepts a path containing `</script>`.
The config is the operator's, so this matters mostly with SM-01.

Fix: escape the title, and escape `<` in inline JSON.

### SM-54 The directory redirect is an open redirect (low)

`serve_static_file.js:30` builds `location: ${mount}${pathname}/` from the decoded path
(`:63`). `GET /%2Fevil.example%2F..%2Fvendor` resolves to the real `vendor/` folder and answers
`301 location: //evil.example/../vendor/`. A `%0d%0a` variant makes `writeHead` throw, which
ends as a 500 and a `serviceman_error` line. This is control host only, which is exposed live.

Fix: build `Location` from the still-encoded path and collapse leading slashes.

### SM-58 The client address trusts forwarded headers on tunnelled connections (low)

`client_address.js:10-14` takes `x-real-ip`, then the first `x-forwarded-for` hop, for
connections that arrive through an agent's inbound door. There is no list of trusted proxies.
The effect is limited to the logged and forwarded address, and the comments say it is
deliberate. It is noted so that nobody later uses this address for access decisions.

## 2. The agent and the machines it runs on

### SM-02 Package names go unquoted into a shell line the root half runs (critical)

`src/agent/src/agent_apt.js:27` builds `${apt} update && ${apt} ${tail(job)}` and runs it with
`/bin/sh -c` at `:28`. `tail()` joins `job.install` or `job.remove` raw at `:80` and `:85`.
The comment at `:72-73` says the names "were read as package names where they were written, so
there is nothing here to quote". That is true only of the host's HTTP route (`RE_TOOL`,
`handle_control_request.js:375`). `agent_serve.js:411-417` forwards `params.names` from the link
unchecked, and `agent_root_serve.js:175-180` takes them from whoever opens the root socket.

Reproduced with the root half run as an ordinary user and the fake apt-get. A name containing
a shell separator ran an extra command that wrote `id` output to a file. A name starting with
`-o` reached apt-get as an option. In production the root half is uid 0, and under
`sudo -n apt-get` an injected dpkg hook option also runs as root.

Anything that can talk to the root socket gets root without a password. That includes the
agent user and every shell service the agent starts as that user. It breaks the promise at
`agent_root_serve.js:16-17`. Combined with SM-01, a web page can create a shell service that
does this.

Fix: check names against the package-name pattern in both halves, and pass argv arrays
instead of a shell line.

### SM-04 Root executes an `agent.js` the unprivileged user can overwrite (high)

`src/main/src/helpers/agent_install_sh.js:338` writes a system unit, run by root with
`Restart=always` (`:340-341`), whose `ExecStart` is `$node_bin $prefix/agent.js --role root`.
For a non-root install, `$prefix` is `$HOME/serviceman-agent` (`:55`) and `$node_bin` may be
`$HOME/bin/node` (`:68`). Both are writable by the user. `agent_update.js:29-30` and the
generated `bin/update` replace that file, and `agent_root_current.js:33-34` asks root to restart
within 30 s once the build differs. Read, not run.

Anything that writes as the user becomes root within 30 s: a compromised service, the host, or
a man in the middle through SM-20.

Fix: install the root copy and its node under a root-owned path, and update it only from root.

### SM-05 The file routes reach the whole filesystem; the docs promise the agent folder (high)

`src/agent/src/agent_fs_path.js:13` is `return path.resolve(os.homedir(), asked);`. An absolute
`asked` discards the home base, and `../` climbs out. It backs `fs_list`, `fs_stat`,
`fs_delete`, `fs_rename`, `file_get` and `tar_get`. `agent_fs_delete.js:10` refuses only `/` and
the home dir itself. `program_install` and `program_step` resolve `params.cwd` the same way
(`agent_program_install.js:9`, `agent_program_step.js:11`). With `cwd: "../victim"`, install wrote
`victim/.serviceman-app` and answered ok. `agent_program_remove.js:12` does check containment, so
install and remove disagree on the boundary.

The docs describe a much narrower agent. `docs/remotes.md:113-115` and `docs/config.md:506-507`
say paths outside the agent's folder are refused. `docs/remotes.md:426-431` says the agent
"runs no shell of its own for the host". The code, and passing tests such as
`tests/remote.test.js:1082-1102` (a machine shell) and `:1150-1260` (read, upload, rename and
delete outside the agent dir), show otherwise. `docs/deploy.md:159` contradicts `remotes.md`
("opens a shell on every machine").

Operators are told about a blast radius far smaller than a control-page compromise has. The
machine shell may be intended. The mismatch is the finding.

Fix: decide the agent's scope and write it down. Resolve file paths under a fixed root and
refuse non-descendants, as `program_remove` already does. Apply the same check to install and
step.

### SM-06 A tar download treats file names as tar options, `--checkpoint-action=exec` included (high)

`src/agent/src/agent_tar_get.js:21` spawns
`tar -cf - -C <dir> <names…>`. `RE_NAME` (`:7`, checked at `:16-20`) allows a leading `-`.

```
agent_tar_get({dir, names: ["--checkpoint=1", "--checkpoint-action=exec=id >pwned-tar", "a.txt"]})
→ pwned-tar: uid=1000(ubuntu) gid=1000(ubuntu) …     (GNU tar 1.35)
```

The names arrive in an `o` frame (`agent_tunnel.js:100-102`). They come from the operator's
selection, so a file on the machine with a hostile name, picked in a "download as tar", runs a
command as the agent user.

Fix: put `--` before the names, and refuse names that start with `-`.

### SM-14 The agent forgets its programs on every reconnect and cannot stop them (high)

`state.programs` is created per link (`agent_serve.js:88`). When the link closes it is only
detached (`src/agent/index.js:180`), and the child keeps running. `agent_program_probe.js:5-9`
answers `{running: false}` for anything not in the current link's map, and
`agent_program_stop.js:11-13` answers `{stopped: false}`.

Reproduced over three successive links. The first `program_start` left the pid alive. On the
second link `program_probe` answered `{running:false, pid:null}`. On the third `program_stop`
answered `{stopped:false}`, and the pid was still alive. After any blip, a `start: always`
program is started again while the old one holds the port. Until today's fix the server link
dropped every 92 seconds, so this fired constantly.

Fix: on link close, kill the programs or keep them in agent-wide state, and re-adopt them by
process group on the next link, as docker containers are adopted.

### SM-19 The agent link is plain HTTP with a bearer token and no peer check (medium)

`agent_connect.js:19,26` picks http or https by URL scheme alone and sends
`authorization: Bearer <token>`. The host serves plain HTTP only (`docs/deploy.md:26-30`). The
server agent dials `http://serviceman:3001`. The token travels only in a header, never in a
URL. In the live deployment tailscale encrypts the transport. Nothing in serviceman checks
the peer, so on any other network the token and SM-02 through SM-06 are one sniff away.

Fix: refuse a non-loopback `http://` URL unless the operator opts in, and document tailscale
or TLS as the requirement.

### SM-20 Self-update writes and runs what the link sends, with no integrity check (medium)

`agent_update.js:22-36` writes `params.text` over its own file and exits so that the service
manager restarts it. The only gate is that the old file contains `modules["agent/index"]`
(`:26`). The `bin/update` path (`:16-20`) re-runs the installer, which fetches the agent with
curl. Neither checks a hash or signature. The path is exercised: the server log has 74 update
calls. Together with SM-19 and SM-04, whoever controls the link replaces the file that root runs.

Fix: sign the bundle, or have the agent verify a hash it already trusts, before the write.

### SM-21 File upload writes through a symlink at the destination (medium)

`agent_file_put.js:27-29,59-66` writes `.<name>.part` and renames it over the name. If
`.<name>.part` already exists as a symlink, the write lands on its target. Reproduced: a victim
file outside the folder was overwritten through a planted `.f.part` link. `RE_NAME` blocks
traversal in the name only. `agent_fs_rename` and `agent_fs_delete` have the same gap. With
SM-05 the host can already write anywhere. This matters for a symlink planted by another local
user or a service.

Fix: open the part file with `wx` and `O_NOFOLLOW`, and `lstat` before the rename.

### SM-22 A hung docker keeps the agent from ever sending hello or redialling (medium)

`agent_serve.js:78-85` awaits `agent_resources()`, which runs `docker version`
(`agent_resources.js:14`) with no timeout. That happens before the hello and before the clock
that carries the beat and the host-quiet watchdog (`:97-128`). With `SERVICEMAN_DOCKER`
set to `sleep 3601`, the agent connected and then sent nothing for 15 s: no hello, no beat, no
watchdog. The host drops a link with no hello after 10 s (`remote_attach.js:23,70-75`). The agent
stays parked in the docker call and never redials until docker answers.

Fix: send hello and start the clock first, and put timeouts on the resources and stats calls.

### SM-23 The agent's dial has no timeout (medium)

`agent_connect.js:15-60` sets no timeout on the request or the upgrade. Against a server that
accepts TCP and never answers, the agent held one connection for 20 s and logged only
`agent_connect_begin`. The backoff loop moves only on resolve or reject. The server log has
12,691 `connect ETIMEDOUT 100.64.0.20:3001`, the kernel's two-minute timeout. A half-open
proxy would hang the agent indefinitely.

Fix: add a request timeout and a handshake deadline that rejects into the backoff.

### SM-33 Agents that dial a unix socket can never update (medium)

The installer fetches the agent with `curl -fsSL "$url/api/v1/agent.js"`
(`agent_install_sh.js:79`), which has no `unix://` branch. The generated `bin/update` fetches
`install.sh` over the socket and then runs it with `--url unix://…` (`:288-295`). Run with
`--url unix:///nonexistent/control.sock`, it failed with `curl: (1) Protocol "unix" not supported`
after creating the folder. `docs/config.md:78` advertises this URL form, and `agent_update.js`
runs `bin/update`, so the automatic update fails every time on such machines.

Fix: give the fetch at `:79` the same unix-socket branch that `bin/update` already uses.

### SM-52 The install script pastes the Host header into shell; the token is on a command line (low)

`agent_install_sh.js:19` writes `url='${url}'`, where the URL comes from the raw Host header
(`handle_control_request.js:1230-1234`), and the route answers before the access check (`:142`).
A script generated for `Host: x';echo INJECTED…;exit 0;'` printed `INJECTED`. Today the header
is set by whoever fetches the script, so it only hits their own copy. `Host: localhost` with no
control port produces `http://127.0.0.1:null`. Separately, the generated `bin/update` runs
`set -- --token "$token"` (`:282`) and then `sh install.sh "$@"`. While it runs, any local user
can read the token in `/proc/<pid>/cmdline`.

Fix: check the host against `^[a-z0-9.-]+(:[0-9]+)?$`, and pass the token through the
environment.

### SM-59 A dead second `tick()` sits in `agent_serve.js` (low)

`agent_serve.js:195-220` defines a top-level `tick(options, state, socket, group)` that reads
`state.tick_at`, `beat_at` and `stats_at`. Nothing sets those fields and nothing calls it. The
live loop is the closure at `:100-127`. It duplicates the `agent_woke` sender site, and it
lacks the host-quiet check, so a later edit to the wrong copy would be silent.

Fix: delete it.

### SM-60 The agent's log is world-readable and carries service output (low)

`agent_log.js:29` opens the daily file with the default umask: 0644 in a 0755 folder,
reproduced. The installer sets `umask 077` only around the env file
(`agent_install_sh.js:93-115`). The log carries every program's stdout and stderr, and the
docker argv of SM-10. The status and root sockets, by contrast, are 0600.

Fix: create the log folder 0700 and its files 0600.

### SM-61 The GNOME helper uses `GLib` without importing it (low)

`agent_gnome_helper.js:90`, `:93` and `:98` call `GLib`, and the file imports only `Gio` and
`Shell`. It runs inside gnome-shell, so the failure would show only on the code path that
reaches those lines. Read only.

## 3. Secrets and logs

### SM-10 The Google OAuth client secret and Sentry DSN sit in world-readable logs (high)

`agent_serve.js:311` logs a docker call as `argv.join(' ')`, and
`docker_argv_from_service.js:26` builds that argv with `--env NAME=value`. The host writes the
agent's line again word for word (`remote_attach.js:192`). Five `agent_call_begin` lines in the
host log carry `--env AUTHWALL_GOOGLE_CLIENT_SECRET=<value>` and `--env AUTHWALL_SENTRY_DSN=<value>`.

### SM-18 Tokens and a client secret sit in a 0644 config, and every write widens the mode (medium)

`data/serviceman.json` is 0644, owned by `nobody`. It holds the four remote tokens (`:21`,
`:33`, `:37`, `:41`) and the authwall service's `AUTHWALL_GOOGLE_CLIENT_SECRET` and
`AUTHWALL_SENTRY_DSN` in its env (`:215`, `:216`). `docs/config.md:440` says secrets are "never in
the config", and a secrets store exists for exactly this: `data/secrets.json` is 0600. A token
lets its holder dial in as that remote and be sent that remote's services and their secrets.

Config writes do not keep the file's mode. `config_remote_add.js:32-34` and
`handle_control_request.js:1368-1370,1572-1574` write the temp file with the default mode and
rename it over the config. A config set to 0600 was 0644 after one machine join. Also, the
default config path `./serviceman.json` (`src/main/index.js:90`), where the README puts it, is
in `.dockerignore` but not `.gitignore`.

Fix: write the temp file with the old file's mode, or 0600, and fsync before the rename. Move
the authwall env secrets into the secrets store. Add `serviceman.json` to `.gitignore`.

### SM-26 Agents and anonymous visitors can forge log lines (medium)

`log_line.js:27` writes a string detail as it is: `typeof words === 'string' ? words : log_words(words)`.
Newlines, ESC and `][` go into the file raw. A detail of
`first\n[2026-01-01T00:00:00.000Z][cfakefakefak][serviceman_end_ok] signal=SIGTERM` wrote two
physical lines, the second a complete forged event. An agent supplies the text, the group uid
and the sender (`remote_attach.js:186,192`). An anonymous visitor supplies the path that
`handle_request.js:121` writes into `request_begin`, and node accepts
`GET /x][cfakeuid00000][remote_refused]`. Keys are not encoded either: `log_words.js:20` turns
`{'a b': 'x'}` into `a b=x`.

In the live logs, 3 lines carry a raw ESC (first `data/logs/20260823.log:13399`). 6,998
`agent_call_stdout` lines carry `[..][..]` tags in their details, and 50 carry raw OAuth `code=`
and `state=` values (first `20260831.log:23328`). The host's own `request_begin` masks the same
callback URLs.

Fix: JSON-quote a string detail that is not plain printable text. Refuse a uid that does not
match `^c[0-9a-z]{11}$` and a sender that is not `^[a-z_][a-z0-9_]*$`.

### SM-46 Query values reach the log through two paths (low)

`server_start.js:146` writes `serviceman_error` with `path: req.url` and `error: error.stack`.

### SM-47 The log writer rotates by local date, dies for good on one failure, and can exceed 2k (low)

## 4. Service lifecycle and the remote link

The repro scripts for this section are in the session scratchpad under `audit-B/`
(`s1`…`s8`). They use a copy of the test fixture with the fake docker.

### SM-11 A link drop during a request marks a running container stopped (high)

`remote_attach.js:247-252` ends the link's streams, and their errors fire on the next tick,
after `remote_services_lost` marks the instance `lost`. `proxy_request.js:48-55` then reads the
`ECONNRESET` as a dead upstream and calls `instance_stopped`: phase `stopped`, remote `null`,
`started_at` `null`. On the next dial, `service_probe.js:25` sees an instance that is not
`lost` and restarts both clocks. So today's clock fix does not apply whenever a request was in
flight. The line written also blames the service's port.

Reproduced (`s1`): `slow answer status 502 phase after drop: stopped remote: null`, then
`started_at kept? false`. Live: `grep -h '\[upstream_error\]' data/logs/*.log` finds 25 lines of
`reason="the link to remote laptop dropped" hint="nothing inside answers on port 3000, check publish.port"`,
for example `data/logs/20260823.log:110`.

Fix: in `proxy_request`, leave an instance alone when its remote is offline or its phase is
`lost`. Stop it only on a real upstream error.

### SM-12 A stop and a start of one instance do not wait for each other (high)

`instance_stop.js:28-44` never waits for `start_promise`. `instance_start.js:34-99` checks
`stop_promise` only on entry, and `start_on` then sets the phase over whatever the stop wrote.
`service_stop.js:25-29` stops `starting` instances too. The reaper, the control page's stop and
a restart all reach this.

Reproduced (`s2`, a container that takes 1.5 s to answer):

- A stop at 30 ms resolved and left the phase `stopped`. The start then resolved with phase
  `running`, and the container ran. The stop was lost.
- A stop at 400 ms killed the container. The start then probed a dead port for its whole
  timeout: `service_start_end_error 8.193s … failures=1 reason="nothing answered … is publish.port (8080) the port …"`.
  That counts toward giving up on the service.

Fix: have `instance_stop` wait for or cancel `start_promise`, for example with a generation
number that `start_on` checks before it sets `running`. Stop `wait_http_answer` once the phase
is no longer `starting`.

### SM-13 A visitor who leaves the queue keeps the slot, and later visits get 504 for good (high)

`pool_acquire.js:17-38` has no way to cancel a waiter. The release is registered only after
the await, with `res.once('close', …)` at `handle_request.js:204` and `socket.once('close', …)` at
`handle_upgrade.js:54`. When the line moves after the visitor has gone, `pool_pump.js:15`
increments `inflight`, and `close` has already fired, so nothing ever releases it.

Reproduced (`s7`, concurrency 1): `after both are over: inflight 1 queue 0`. The reaper sees a
busy instance and never stops it, and every later visit answers 504.

Fix: drop the waiter when the request or socket closes, and release at once when the response
is already destroyed after the acquire.

### SM-15 A machine dialling in tears down copies of the service running on other machines (high)

`remote_services_wake.js:14-19` probes every service that lists the remote that woke.
`service_probe.js:25-38` re-adopts instances already `running` elsewhere and calls
`agent_reset`, whose `instance.agent.destroy()` (`agent_reset.js:11-12`) cuts their in-flight
requests. Those requests then hit SM-11. The next visit starts a second container, and the
first is orphaned.

Reproduced (`s6`, `remotes: ["vps1", "vps2"]`, running on vps2, a slow request in flight, vps1
dials in): `service_adopt_ok … remote=vps2`, then `upstream_error … reason="socket hang up"` and
`request_end 502`. Afterwards: `next visit 200 on vps1 | vps1 container running true | vps2 container running true`.
Every service in the live config names one remote, so this has not happened there.

Fix: probe only instances that are `lost` or `stopped`, or whose remote is the one that woke.
Never reset a running instance whose remote did not change.

### SM-27 A lost instance is adopted wherever a copy is found, orphaning the other (medium)

`service_probe.js:45-57` walks the candidate machines in config order, not the instance's own
machine first. The match is by spec hash only (`docker_probe.js:11`), with no container identity.
Since today's fix, a lost copy found on a different machine also keeps the old copy's clocks.

Reproduced (`s4`): the first visit ran on vps1. vps1's agent was killed, the instance went `lost`,
and the second visit started a copy on vps2. When vps1 returned, `service_adopt_ok … remote=vps1`
followed. After the idle stop, vps1's container was stopped and vps2's was still running,
tracked by nothing. Multi-machine services only.

Fix: probe `instance.remote` first. When a copy turns up elsewhere, stop it or refuse it
rather than switching. Keep the clocks only when the machine and container id match.

### SM-28 The restart backoff never grows for exit 0 or a signal (medium)

`program_ended.js:25-27` sends exit 0 and signals through `instance_stopped`, which clears
`started_at`. Line 36, `if (Date.now() - instance.started_at > SETTLED_MS) instance.restarts = 0;`,
is then always true, so the wait at `:39` is always 1 s. Reproduced (`s3`, `sleep 0.1; exit N`,
restart always, 9 s): exit 0 gave nine lines of `program_restart_wait … in=1.000s restart=1`.
Exit 3 gave 1, 2, 4 and 8 s. A program killed for memory under `restart: always` restarts once a
second forever.

Fix: read `started_at` before `instance_stopped` clears it, or keep a separate clock.

### SM-29 A pending restart survives a definition edit and runs the old command (medium)

`app_apply_config.js:44-55` drops a changed service object and calls only `agent_reset`. It never
clears `instance.restart_timer` (set at `program_ended.js:42-45`), and `restart_now` (`:56-66`)
checks only the old object's `stop_promise`. Reproduced (`s8c`): a crash-looping `sleep 0.2; exit 3`
was edited to `sleep 30`. Four seconds after the new config applied, the old object logged
`service_start_begin` and `program_begin … argv="/bin/sh -c sleep 0.2; exit 3" … started=true`.
When the new program was already running, the old object logged `start_end_ok started=false` and
claimed the new pid (`s8`).

Fix: clear the restart timers of every dropped service, and mark the dropped object retired so
that `restart_now` returns.

### SM-30 Throughput blasts pile up on a slow link (medium)

In `remotes_measure.js:40-50`, a measurement stays owed until `measured_at` is set, which
`remote_measure.js:23` does only after a blast returns. Nothing marks a blast in flight, so every
10 s tick starts another ping and another 1 MiB blast (`remote_blast.js:15`). If each blast
takes over 60 s, they all time out, `measured_at` stays null, and 2 MiB per 10 s goes on forever
over the link it measures. A simulation (`s5_blast_pile.js`) reached six blasts and 6.0 MiB in
flight by the sixth tick. Live measurements include 131 KB/s on laptop, 142 KB/s on desktop and 144 KB/s
on server, all below that break-even. server blasts timed out on 2026-09-23 at 21:09 and 21:24.

Fix: keep a measuring flag per remote, and set `measured_at` when the blast starts, or back off
after a failure.

### SM-31 One stream's exception drops the whole machine link (medium)

`remote_attach.js:49-57` wraps all of `frame_read` in one try/catch that ends with
`socket.destroy()`. A data frame reaches `push()`, which calls http parsers and pipes
synchronously, so a bug in one request handler drops every stream on that machine and marks all
of its services lost. The same try covers the hello and `tunnel_inbound`'s `JSON.parse`. Live:
`data/logs/20260830.log:31642`,
`[remote_link_error] remote=phone reason="Invalid character in header content [\"content-disposition\"]"`,
then `remote_offline remote=phone held=20s`, five times in four minutes. That call site was fixed
later with a `content_disposition` helper, but the catch-all remains.

Fix: catch per stream and destroy only that stream. Destroy the link only on framing errors.

### SM-56 One failing probe stops the wake for every later service (low)

`remote_services_wake.js:11-27` awaits `service_probe` (`:19`) in a loop with no per-service
catch. A rejected call aborts the loop, so later services are neither adopted nor started, and
one `remote_service_error` line is written. The six live occurrences are all link drops.

Fix: catch and log per service.

### SM-57 `serviceman_end_error` can never be written (low)

`src/main/index.js:257`, `await Promise.all(stops).catch(function () {});`, swallows every
failed stop, so the error branch at `:226-227` is dead. `docs/logs.md` describes the line ("A
program would not stop; it left anyway, and says why"). The live count is 0.

Fix: collect the failed stops and write them.

## 5. Config

### SM-32 `socket_mode` accepts nonsense, and the agent's door is chmodded after listen (medium)

`config_from_json.js:180` parses the mode with `parseInt(String(json), 8)`, and
`server_start.js:75` applies it with `chmodSync`. Results: `384` gives 0o003, so others may
connect and the owner may not. `420` gives 0o420. `"0999"` and `"0o600"` give 0. `"0700abc"`
gives 0o700. For the control socket, that mode is all that guards a passwordless API.

The agent's http door does the same in `agent_http_serve.js:91-99`: `"0660x"` gives 0o660, and
`"9"` gives NaN, which means no door. It chmods in the listen callback (`:53-56`), so the socket
is briefly connectable with the umask's mode.

Fix: accept only `^0?[0-7]{3}$`, and set the umask before `listen`.

### SM-34 Container names collide across services (medium)

A service `web` with `instances.max` 2 next to a service `web-2` gives both a container named
`serviceman-web-2` (`docker_container_name`). `config_from_json.js:100-116` does not check for
this. The second start finds a container carrying another spec label and recreates it, taking it
from the other service. The names were reproduced. The docker behaviour was read from the code.

Fix: refuse a name equal to another service's `<name>-<n>` for n up to its maximum, or join
with a character names cannot contain.

### SM-35 Kept-volume folders collide, and `:/..` maps to every service's storage (medium)

`volumes_from_json.js:53-56` (`slug_of`) maps `:/app/data`, `:/app-data` and `:/App/Data` all to
`svc/app-data`, so two paths of one service silently share one folder. `:/` gives `svc/`, and
`:/..` gives `svc/..`, which `volume_text` renders as `<agent>/data:/..`. That mounts the agent's
whole data folder, with every service's storage.

Fix: refuse targets that make the same slug, `..` segments and `/`, or use a reversible
encoding.

### SM-36 Two sets of defaults; `config/index.js` applies at boot and drops on first save (medium)

`src/main/index.js:50` merges `config/index.js` under the file (`profile_from_db.js:10`). The
merge is shallow. That file says listen 3000, control 3001 and a control socket at
`./data/serviceman.sock`. The docs disagree with it and with each other:

- `docs/config.md:47-48,57,96,98` say 8080, 8081 and no socket.
- `README.md:19` says 8081 and 8080.
- `docs/overview.md:134` says 3000 and 3001.

Every later writer calls `config_from_json(json)` without that base: `config_remote_add.js:30`
and `handle_control_request.js:1367,1565,1583`. On a file with no `listen` or `control`, the
ports were 3000, 3001 and the socket at boot, and 8080, 8081 and no socket after one machine
join. `app_apply_config.js:26` then reports "listen or control changed — waits for a restart"
when nothing changed. A file that sets `control.exposed` alone loses the whole default control
object, port and socket included. `config/index.js` is not documented anywhere.

Fix: keep one settings object on the app and use the same merge everywhere, or drop
`config/index.js`. Document one set of defaults.

### SM-49 Durations have no range; `25d` answers every queued request with 504 at once (low)

`duration_ms_from_text.js:11-13` takes any number: `-5` gives -5000 and `1e400` gives Infinity.
Strings go up to `30d`, 2,592,000,000 ms, which is over 2^31-1. On node 24,
`setTimeout(2592000000)` fires after 1 ms (tested), so `request_timeout: "25d"` makes
`pool_acquire.js:23-27` answer queued requests with 504 at once. That part was read from the
code. `start_timeout` of `false`, `"off"` or `0` parses to null or 0, and `wait_http_answer.js:39`
then fails the start at the first unanswered probe.

Fix: refuse zero or less, except the documented off values, and anything over 2,147,483,647 ms.
Refuse off for `start_timeout`.

### SM-50 Unknown keys and wrong types load silently (low)

`docs/config.md:11` promises that `--check` refuses what would fail at the first request.
These load without a word:

- `policy.stop_afer_idle`, misspelt, falls back to the default.
- `instances: 3` becomes min 0, max 1.
- `prepull: "no"` becomes true.
- env `{A: 1, B: {x: 1}, C: null}` becomes docker argv `B=[object Object]` and `C=null`.
- `run_args: "--rm"` becomes the argv `-`, `-`, `r`, `m`.
- Hostnames are checked only for lowercase and `:` (`assert_service_valid.js:114-125`), so
  `a b"c`, a name with a tab and `<`, `a.test?x` and `a.test.` all load.
- `remotes: [null]`, `services: [null]` and `hosts: [42]` throw bare TypeErrors with no field
  named. `"socket": null` does too (`config_from_json.js:58,65` check only for undefined).

Fix: type-check each field against a list of allowed keys.

### SM-51 The example's placeholder token loads (low)

`examples/serviceman.full.json` uses the token `replace-me-with-openssl-rand-hex-32`, 35
characters. `assert_remote_valid.js:11` asks only for 16. A copied example accepts any agent
that holds a publicly known token.

Fix: require 32 or more characters, and refuse known placeholders.

### SM-38 Blocked `localStorage` blanks the whole control page (medium)

`src/main/public/index.html:11` and `:14` read `localStorage` before the first paint with no

## 10. What is good

- **The link protocol is careful.** Tokens are compared hashed with `timingSafeEqual`, in
  constant order across remotes (`handle_remote_upgrade.js:250-287`). There is one agent per
  token (409), and a removed remote gets a distinct 410. Streams have real credit flow control
  with a 256 KiB window and odd and even id halves. A dropped link rejects every pending call
  and ends every stream, so nothing waits on a dead machine.
- **Config writes are serialised.** They go through one promise chain (`config_locked`),
  temp-then-rename, with a hash check that answers 409 on drift. Twenty concurrent service
  creates all landed. The validator refuses duplicate names, duplicate host and path pairs,
  a service on the control hostname, shared tokens, and busy thresholds in the wrong order,
  with messages that name the field.
- **DNS rebinding is closed.** `control_host_allowed` answers only loopback names and the
  configured control names. Static and skin serving refuse `../`, encoded traversal and NUL.
  Hop-by-hop headers are stripped both ways.
- **Starts and stops coalesce.** Two starts share one start, and two stops share one stop. A
  request that arrives while the reaper stops a service gets a clean start afterwards. The
  reaper skips anything in flight or queued. Autoscale has separate up and down clocks and a
  cool-down, so it cannot flap.
- **Process groups are handled properly.** `program_kill` signals the group and waits for it,
  treating `EPERM` as alive. Every `docker run` has `--init`. Both notes on signals describe
  fixes that are in the code.
- **The log shape holds at scale.** All 352,714 host lines have three fields, a `c`-plus-11
  uid and at most 1,992 bytes. Trimming never cuts inside a utf-8 sequence. The host's own
  request lines mask query values.
- **Secrets have a real store.** It is 0600 and written temp-then-rename. The page sees only
  names and lengths. Secret files on the agent are 0600 and mounted read-only.
- **The control page is sturdy where it was tested.** Hostile titles and env values render as
  text in the overview. The theme switch has two states, is set before first paint and
  persists. The page fits 375 px without sideways scroll. `dragstart` is cancelled
  document-wide. Every compound Vue condition is parenthesised. Vendored libraries match the
  lockfile byte for byte. The heap stayed flat over 2.5 minutes.
- **The tests are end to end without docker.** Real agents dial over the real link, and a
  file-locked fake docker stands in for the daemon. 165 of 165 pass in 83 s, including log
  discipline, redaction and today's watchdog change in both directions.
- **Dependencies are clean.** `npm audit` reports nothing, and Vue is one patch behind.
